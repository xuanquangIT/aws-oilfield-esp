## Findings addressed in this revision

1. Realtime guessed physical Lambda names; wiring now uses CDK references and stream-specific policies live in realtime to prevent dependency cycles.
2. Native process failures could pass unnoticed in PowerShell; shared helpers check exit codes.
3. Realtime needed manual teardown; the wrapper now attempts teardown on success or failure. Process termination or laptop loss can still bypass it.
4. Kinesis was on-demand for a three-event/second lab; default is now one provisioned shard.
5. Batch command returned before completion and required a manual crawler; wrapper now waits and checks both results. This is still client-side orchestration.
6. Full reset silently deleted data and hid a teardown error; reset now requires -DeleteData and stops on failure.
7. Long-lived Lambda logs and implicit Glue retries/concurrency lacked bounds; explicit controls added.
8. Documentation contained unresolved citation tokens and service-name-only exam mapping; replaced with source links and an evidence-based plan.
9. Core resource/output shared the AthenaWorkGroup construct ID and synthesis failed; output construct renamed while preserving the CloudFormation output key.
10. M1's contract enforcement was implemented but unverified in AWS; redeployed core and reran batch (504/504 rows, 504 distinct event IDs, schema_version=1 via Athena) plus a manual Kinesis quarantine smoke test proving invalid records never reach raw/realtime or LatestState while valid ones do. See docs/09-RUNBOOK.md section 6.5.
11. Sustained anomalies sent one SNS email per record (159 emails in one `low_flow` demo, no cooldown); `src/anomaly_detector/handler.py` now tracks per-(esp_id, rule_id) episode/cooldown/recovery state in a new `AlertState` table, verified offline by a regression test asserting 50 consecutive anomalous records send exactly one alert (`tests/test_anomaly_detector.py`).
12. DynamoDB latest state was an unconditional last-write-wins `put_item` with numbers stored as strings; `src/stream_processor/handler.py` now writes conditionally (accepts a strictly newer `timestamp` only) with Decimal numeric types, so a late or duplicate-delivered record can never regress state, verified against the `duplicate`/`late` fixtures (`tests/test_stream_processor.py`).
13. Raw realtime history was keyed by the Kinesis sequence number (transport metadata, not a stable identity); the object key is now the event's own `event_id`, so replaying or redelivering the same event is an idempotent overwrite instead of a new object.
14. M2's fixes were implemented but unverified in AWS; redeployed core (new `AlertState` table + rebundled Lambdas) and the realtime stack standalone, then proved both fixes with real traffic. Conditional state: sent a newer-timestamp record for ESP-101 (accepted, numeric fields stored as DynamoDB `N`), then an older-timestamp record for the same pump (rejected by the `ConditionExpression`, `LatestState` unchanged), with both events still present as separate objects in `raw/realtime/` keyed by their own `event_id`. Alert cooldown: ran the `low_flow` scenario for 2 minutes (360 records across 3 pumps); `AlertState` recorded exactly 4 episodes (3 active with a `cooldown_until` ~5 minutes out, 1 recovered) and CloudWatch's `AWS/SNS NumberOfMessagesPublished` showed exactly 5 messages published, versus the 159 emails the same class of run produced before M2. See docs/09-RUNBOOK.md section 6.6.
15. M3 had only a CSV overwrite path, so it could not reconcile archived realtime records or protect a prior publication. The replacement accepts a checksum-bound manifest and distinct publication run ID, revalidates both raw sources through `contract.py`, preserves provenance, fail-closes conflicting event IDs, records input accounting/quality output, writes immutable partitions and updates `curated/publication/current.json` only after quality passes. Pure offline tests cover manifest stability and duplicate/conflict accounting; Glue/Athena behavior is not yet AWS-verified.
16. First M3 AWS launch exposed two integration faults: overlapping `BucketDeployment` prefixes pruned Glue's extra contract file, and a positional CSV schema shifted historical fields after optional realtime-only columns. One script deployment now owns `scripts/`; historical CSV is projected/cast by header name; publication requires accepted rows from both source kinds. The failed/one-source run is not M3 acceptance evidence.
17. M3's exit gate (docs/06-DELIVERY-AND-LEARNING.md) required five AWS proofs; all five are now verified with real runs. (1) Mixed sources: a corrected run's quality report showed `historical_silver_rows=72` and `realtime_silver_rows=180` together, `quality_passed=true`. (2) Accounting balances: `unexplained_rows=0` with `accounted_rows == input_rows` (684) on every passing run. (3) Deterministic rerun: replaying the exact same frozen manifest (`m3-manifest-d22b7b3bf40c47abb60ce9d4edc46dcb`) in a second independent Glue run produced an identical `canonical_data_sha256` (`9bbba6f0...ad3e05`) and identical counts. (4) Isolated backfill: after publishing 2026-09-12, a backfill run for the unrelated day 2026-09-13 left the 2026-09-12 Parquet object's S3 ETag and size byte-for-byte unchanged, while writing its own new `publication_run_id` partition (immutable run-scoped output, never overwritten). (5) Partition pruning: an Athena query against the crawled `silver` table scanned 7,351 bytes with no predicate versus 632 bytes (~91% less) with an `event_date` predicate, both via `AWS/Athena` `Statistics.DataScannedInBytes`. A final full-window run (2026-09-12..13, both sources, 325 silver rows, 6 gold rows, `quality_passed=true`) is the currently published run. See docs/09-RUNBOOK.md section 6.7.
18. M4 is AWS-accepted. An independent Step Functions execution ran Glue, then started/polled the crawler to a fresh `READY`/`SUCCEEDED` crawl without client orchestration. G4's deployed-role simulation returned `implicitDeny` for all five forbidden actions. A normal one-minute run drained 180/180 acknowledged records into raw S3 with no missing/quarantine records. An independent Scheduler invocation at `2026-09-12T08:38:13Z` deleted a realtime stack without a connected client; the reaper logged `outcome=deleted` at `08:38:47Z`, after which both realtime stack/schedule were absent. On 2026-09-13, two independent export/reset/recreate/restore drills preserved 2,039 S3 objects (2,134,080 bytes) and DynamoDB counts of 3 `LatestState`/0 `AlertState`; the paired verifier read each restored object and compared SHA-256 plus canonical DynamoDB item content to its export manifest. The final reset left only the recreated core, with no Kinesis or Scheduler schedules.
